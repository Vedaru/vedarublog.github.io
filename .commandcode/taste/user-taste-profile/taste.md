# User Taste Profile
- Writes in casual, lowercase prose without capitalizing sentence starts (e.g. "when i return to the homepage..."). Treat this as a personal style, not a mistake. Confidence: 0.7
- Reports bugs as direct, short problem statements followed by a clear directive ("check why and fix") — expects autonomous investigation and root-cause analysis rather than clarifying questions. Confidence: 0.6
- When the user has already confirmed a bug on the live deployed site (e.g. real Chrome on Cloudflare after cache clear), do NOT spend many turns trying to reproduce locally with various viewports/flags, and do NOT spin up elaborate measurement/sampling scripts to "prove" the issue is gone. Trust the live-site evidence and go straight to the fix. User explicitly corrected twice: "you are spending too much time on trying to get the exact page" and (implicitly) by redirecting to the live URL after a long local measurement loop. Confidence: 0.9
- After a code change is complete and builds cleanly, do NOT spin up local preview servers, run headless-browser sanity checks, or otherwise verify behavior locally before pushing. Push to GitHub and let CI/CD handle the rest — the user will test the live deployment themselves. User explicitly said: "you are too slow just push to github and let the cicd to the rest of the work and i'll check and test myself". Confidence: 0.95
- When fixing a regression on the live site, identify the root cause from the deployed HTML/JS directly (e.g. via `web_fetch` of the live URL, grep on the built `dist/` output) and apply the minimal fix to source. Don't spin up local preview servers to reproduce, don't write measurement scripts to "prove" the cause — just read the actual shipped markup, find the bug, edit the source, rebuild, push. Confidence: 0.9
- Don't commit to a root-cause theory and ship a fix before confirming it actually explains the reported symptom. The user will push back hard if the proposed fix doesn't match what they're observing (e.g. "no, i don't think this is the problem, because when the page is stuck there still is no main grid on the page"). Keep digging — inspect the live DOM, check all the pieces in play (other CSS classes, layout components, animations) — until the explanation accounts for the exact symptom. Confidence: 0.9
- When debugging rendering/visibility bugs, the issue may not be in the JS or the obvious element — also check site-wide CSS classes applied to broad containers (e.g. `.onload-animation` with built-in `animation: fade-in-up forwards`), and trace how animations get triggered (CSS-only vs. JS-driven). Don't stop at "the container has opacity-0" if the user says even the grid chrome isn't rendering. Confidence: 0.7
- When optimizing performance or implementing features, look at the upstream reference repo (https://github.com/LyraVoid/Mizuki — this project is a fork) for the canonical implementation before inventing a custom approach. The user explicitly directs to it for ideas ("you also can check this for more ideas"). Prefer matching upstream patterns (e.g. `<Image>` with `widths={[200, 400, 600]}` + `sizes` for responsive srcset) over homegrown solutions. Confidence: 0.85
- When the user suspects a class of cause (e.g. "i sus that the stuck might be because of a race or a parallel download"), take the suspicion seriously as a working hypothesis and investigate it directly rather than dismissing it. The user's intuitions about web platform behavior (race conditions, parallel download limits, network contention) are often correct and worth verifying with concrete evidence (e.g. measuring image payload sizes, checking `import.meta.glob`/Astro image pipeline behavior). Confidence: 0.8
- Writes casual lowercase prose with typos/abbreviations and treats that as natural style ("i sus", "pic compress mods", "preceed with", "you also can check"). Don't correct grammar or normalize phrasing in responses — match the user's casual register. Confidence: 0.75
- Strong cost-sensitivity / preference for free options. When presented with options that include a paid tier, will immediately ask "is this free??" before committing to anything. Default to exploring free / already-paid-for paths first (free tier services, existing infrastructure, clever workarounds) before recommending paid services or new infrastructure. Confidence: 0.85
- Prefers reusing existing infrastructure over adding new services. When facing a new problem, first asks whether it can be bolted onto something already running (e.g. "i already have my blog deployed on cloudflare, so can meting api be deployed on it too?") rather than spinning up a separate service or account. Surface consolidation opportunities before suggesting new deployments. Confidence: 0.8
- When SSR markup produces a layout that differs from what JS-rendered markup produces on every subsequent visit (a FOUC/format-jump), prefer fixing it by duplicating the post-JS CSS selectors to also key off attributes that ARE present at SSR time (e.g. `<html data-post-list-layout="list">` set by the inline head script). Don't try to add the runtime classes to SSR markup or move JS earlier — just make the CSS resolve to the same styles whether the attribute or the class is present. This was accepted without pushback. Confidence: 0.85
- After a build is verified clean, do not run additional verification (grep on dist for symbols, regex matches on output, multiple `ls` calls on dist files, etc.) just to "confirm the fix made it into the bundle". One confirmation grep is enough, then move to commit and push. The user doesn't want to watch you grep the same files five different ways. Confidence: 0.85
